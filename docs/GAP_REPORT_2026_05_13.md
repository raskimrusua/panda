## Section 1 — DB structure + formula correctness

| Concern | Status | Notes |
|---|---|---|
| Tenant isolation across all writes | ✅ | Every business write goes through `BelongsToTenant`'s global scope; the seeder calls `$tenant->makeCurrent()` and trusts the trait. Nothing leaked across tenants in the test runs. |
| ULID PKs everywhere | ✅ | Tenant, User, Crop, Season, SeasonActivity, InputListItem, CostEntry, HarvestLog, DiseaseDetection — all ULID. FK migration ordering bug (PR #3 fix) holds. |
| Decimal precision on KES amounts | ✅ | All `*_kes` fields are `decimal(*, 2)` cast; no float drift surfaced when summing 34 cost entries × 19 harvests. |
| Date casting (TZ-safe) | ✅ | `planting_date` + `harvested_at` + `incurred_at` cast as `date` not `datetime`; no Frankfurt-vs-Nairobi drift. |
| Soft delete on Tenant | ✅ | `--fresh` test asserts the tenant gets a fresh ULID; `forceDelete()` confirmed working. |
| Engine adjustments (greenhouse / drip) | ⚠️ | Greenhouse `pesticide × 0.6` flag is set in `engine_metadata`, but the *actual* pesticide quantity reduction happens in `inputs_per_acre` only — not surfaced in the per-season UI. The user can see "greenhouse adjustment applied" only in raw JSON. **To do**: render the adjustment list as a badge or chip on `SeasonDetailPage`. |
| Activity completion progression | ✅ | The closed season has all 11 activities done; harvesting season has ~9 done; planning season has 0–1 done. Realistic for screenshots. |

### Formula spot-checks (12-month dataset)

- Closed season (1.5 acres, drip, weeks 0–46):
  - Total costs ≈ KES 51,000 (1.5× the per-acre baseline of ~34k)
  - Total harvest ≈ 1,650 kg picked / ~1,500 kg sold
  - Revenue ≈ KES 95,000 → gross margin ≈ KES 44,000 (~46%) ✅ realistic
- Greenhouse season (2 acres, weeks 0–20):
  - Pesticide cost reduced by ~40% vs drip baseline (engine flag held)
  - Yield uplift ~30% (seeder's hardcoded multiplier matches engine flag intent)

**Open question:** the engine writes the greenhouse adjustment as a *flag* (`'greenhouse_reduces_pesticides_by_40pct'`) but doesn't currently re-compute the input quantity. The seed mimics the expected uplift in `seedHarvests()`. **To do**: have the engine actually apply the multiplier to `InputListItem.quantity_scaled` (currently it doesn't), so the Inputs tab reflects the saving.

### CRUD priorities (ranked)

1. **Season abandon** (mark `STATUS_ABANDONED`) — without this a mistaken season clogs the list forever. ~½ day.
2. **Cost/Harvest edit + delete** — every farmer will mistype at least once a month. Use soft-delete so the audit trail survives. ~1 day.
3. **InputListItem qty override** — common case: farmer buys 30kg of a 50kg suggested item. Should not require admin intervention. ~½ day.
4. **DiseaseDetection list view** in PWA — currently scattered; pull into `/disease/history`. ~½ day.

## How to regenerate this report

After each pilot-ready milestone, re-run the seed and re-walk the matrix:

```bash
docker compose -f docker-compose.prod.yml exec app \
  php artisan panda:seed-demo --months=12 --fresh
```

Then click through every screen on `app.panda.shira.farm` and update the
status column. The matrix is the single source of truth for "are we ready
to ship to 200 farmers?"
